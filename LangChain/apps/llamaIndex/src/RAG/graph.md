## 我们的实现 vs Microsoft GraphRAG 完整对比

### 整体架构对比

```
我们的:
文档 → 切分 → LLM抽三元组 → 邻接表Map → BFS连通分量 → 单层摘要
                                                         ↓
                                         用户查询 → NER → BFS遍历 → 生成

Microsoft GraphRAG:
文档 → 切分 → LLM抽实体/关系/声明/协变量 → 实体消歧 → 知识图谱(Neo4j)
       → Leiden层次社区检测 → 多层社区摘要(level 0/1/2...)
                                                         ↓
                                         用户查询 → 查询路由
                                           ├─ Local Search → 实体子图 → 生成
                                           ├─ Global Search → 社区摘要聚合 → 生成
                                           └─ DRIFT Search → HyDE+社区+局部 → 生成
```

### 逐项对比

| 维度 | 我们的实现 | Microsoft GraphRAG | 差距等级 |
|------|-----------|-------------------|---------|
| **社区检测** | BFS 连通分量（平面） | Leiden 算法（**层次化**，多级社区） | **核心缺失** |
| **社区摘要** | 单层，每社区 1 个摘要 | **多层**（Level 0~2），从微观到宏观 | **核心缺失** |
| **实体消歧** | 无（"CRISPE框架"和"CRISPE 框架"算两个实体） | 用 Embedding + LLM 做**实体解析合并** | **核心缺失** |
| **三元组抽取** | (主体, 关系, 客体) 纯文本 | 实体 + 关系 + **声明(Claim)** + **协变量(Covariate)** | 中度缺失 |
| **查询模式** | 仅 1 种（NER→BFS→生成） | **3 种**：Local / Global / DRIFT | **核心缺失** |
| **全局查询** | ❌ 不支持（问"提示词框架有哪些分类？"只能局部回答） | ✅ 聚合多个社区摘要，回答**跨主题问题** | **核心缺失** |
| **DRIFT 搜索** | ❌ | ✅ 先用 HyDE 匹配社区 → 生成追问 → 局部精搜 → 迭代 | 扩展功能 |
| **声明提取** | ❌ | ✅ 提取带属性（状态、时间、来源）的断言语句 | 中度缺失 |
| **时间推理** | ❌ | ✅ 提取协变量，支持时间维度推理 | 扩展功能 |
| **自动调优** | ❌ 手动写 Prompt | ✅ Auto-tuning，自动适配新领域 | 扩展功能 |
| **大规模支持** | 单文件（Map 内存） | 万级文档（Neo4j 持久化） | 扩展功能 |

### 核心功能缺失（3 项）

#### 缺失 1：Leiden 层次社区检测

当前 BFS 连通分量把所有连通的实体分成一个社区，比如你的知识库里所有"提示词框架"都在一个大社区里。**Microsoft 用 Leiden 算法做层次化分割**：

```
Level 0（最细）:  "CRISPE框架" + "Capacity and Role"  → 一个微社区
                  "CoT" + "链式思考"  → 另一个微社区

Level 1（中层）:   "提示词框架" + "推理技术"  → 两个微社区合并

Level 2（最粗）:   "Prompt Engineering"  → 所有框架和技术合并
```

这样：
- **局部查询**（"CRISPE框架的C是什么"）→ 用 Level 0 就够了
- **全局查询**（"提示词工程有哪些分支"）→ 聚合 Level 2 摘要

#### 缺失 2：Global Search（全局查询）

我们没有"全局查询"模式。当用户问 **"提示词框架有哪些分类"**（需要跨多个社区理解）时，我们只能从匹配的实体出发 BFS 遍历，但 BFS 可能只走到一个社区。

Microsoft 的 **Global Search** 做法：

```
1. 计算 query 与所有社区摘要的向量相似度
2. 选出 Top-K 相关社区摘要
3. 对这些摘要做 map-reduce 聚合
4. LLM 生成综合回答
```

#### 缺失 3：实体消歧

你之前遇到的 `"CRISPE 框架"` vs `"CRISPE框架"` 问题，本质就是缺少实体消歧。Microsoft 在构建图谱后，会用两步解决：

```
Step 1: 用 Embedding 找到相似实体对（向量余弦相似度 > 阈值）
Step 2: 用 LLM 判断是否需要合并
Step 3: 合并实体（合并关系边，保留原始引用）
```

### 我们能低成本补齐哪些？

按投入产出比排序：

| 改进项 | 难度 | 代码改动 | 提升效果 |
|-------|------|---------|---------|
| **1. 实体消歧**（归一化+LLM合并） | ⭐⭐ | ~40 行 | **高** — 解决"CRISPE框架"匹配问题 |
| **2. Global Search**（社区摘要向量检索） | ⭐⭐⭐ | ~50 行 | **高** — 支持跨主题问题 |
| **3. 声明提取**（不仅仅是三元组） | ⭐⭐ | ~20 行 | 中 — 更多上下文信息 |
| **4. Leiden 分层社区检测** | ⭐⭐⭐⭐ | ~80 行 | 中 — 当前数据规模下收益有限 |
| **5. DRIFT 搜索** | ⭐⭐⭐⭐⭐ | ~150 行 | 低 — 需要多层社区摘要先就位 |

**最推荐的三个改进**（按顺序）：
1. **实体消歧** — 解决当前最痛的匹配问题
2. **Global Search** — 让系统支持"全局性问题"
3. **声明提取** — 丰富三元组的表达能力

### 当前你需要补哪些？

这取决于你的目标：

- **学习目的**：当前实现已经覆盖了 Graph RAG 的核心思想（实体抽取 → 建图 → 社区 → 查询），缺失的是**工程化的细节**
- **生产目的**：建议先补**实体消歧**和 **Global Search**，然后用 Microsoft GraphRAG 的 Python 版本（[GitHub](https://github.com/microsoft/graphrag)）做正式场景
