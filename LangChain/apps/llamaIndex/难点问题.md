# RAG 学习中的难点问题

---

## 1. 🔍 检索召回盲区 (Retrieval Blind Spot)

> 涉及架构：Agentic RAG、Adaptive RAG（Iterative 路径）

### 1.1 三个核心问题

```
Query Underspecification（查询欠指定）
  └─ 用户问题太宽泛，检索器不知道该找什么

Search Surface Area Problem（搜索表面积问题）
  └─ 单 query 只探索了 Embedding 空间的一个小区域

Breadth-First Failure（广度优先失败）
  └─ "列举所有 X"类型的问题在单 Agent 系统中尤其困难
```

### 1.2 真实案例：Agent 只检索到 CRISPE

**问题**：用户问"prompt 常用框架有哪些"，Agent 只返回了 CRISPE 框架。

**根因**：
```
用户："prompt常用框架有哪些"
  ↓
Agent 发送 retrieve["提示词框架"]（单 query）
  ↓
向量搜索 → topK=5 → chunk 0 排第一（包含总述 + CRISPE详解）
  ↓
Agent 换关键词 → 依然是模糊 query → 还是 chunk 0
  ↓
5 轮用完 → "目前信息主要集中在CRISPE框架上"
```

**深层因素**：

| 因素 | 说明 | 解决方案 |
|------|------|---------|
| **Chunk 分布不均衡** | 8 个框架分散在 5 个 chunk，CRISPE 在 chunk 0 独占详解 + 总述 | 调整 chunk 策略或使用 query 扩展 |
| **单 query 召回盲区** | 一个泛查询无法覆盖所有框架的 embedding 空间 | 多 query 并行检索 |
| **Agent 不换关键词** | 5 轮都用相似的关键词，反复命中同一个 chunk | Poka-Yoke 工具设计 |

**解决方案演进**：

| 版本 | 方案 | 效果 |
|------|------|------|
| v1 | Prompt 引导多关键词 | ❌ LLM 记不住用逗号分隔 |
| v2 | 工具内部自动 query expansion | ✅ |
| v3 | Poka-Yoke 工具设计（Anthropic 推荐） | ✅ 智能封装在工具内部，不让 LLM 自己做决策 |

> 参考代码：`RAG/8.Agentic RAG.ts` — `expandQuery()` 函数 + retrievalTool（第 119-209 行）

## 2. ⚖️ Grader 评分困境（Corrective RAG）

> 涉及架构：Corrective RAG

### 2.1 评分标准的两难

| 标准 | 问题 |
|------|------|
| **宽松**（提到即高分） | 评分给 7/10，但 LLM 说"未找到相关内容"——**高质量误判** |
| **严格**（解释了才算高分） | 可能漏掉部分相关的片段 |

**教训**：评分标准需要明确区分"提到"和"回答了"。

### 2.2 路由决策陷阱

**错误做法**：用平均分做路由决策。

**案例**：1 个好 chunk（8 分）+ 4 个噪声（1 分），平均分 = 2.4 → 错误降级到 low ❌

**正确做法**：用 `maxScore + refinedCount` 联合决策：

| 场景 | maxScore | refinedCount | 路由 |
|------|----------|-------------|------|
| 问答库（1个好chunk + 4个噪声） | 8 | 1 | high ✅ |
| 全部高度相关 | 9 | 5 | high ✅ |
| 部分沾边 | 4 | 2 | medium ✅ |
| 完全不相关 | 1 | 0 | low ✅ |

### 2.3 Top-K 与成本权衡

| Top-K | 每次查询 LLM 调用次数 | 噪声风险 |
|-------|----------------------|---------|
| 2 | 3 次（评分×2 + 生成） | 低 |
| 3 | 4 次 | 中 |
| 5 | 6 次 | 高 |

> K 值越大，越需要 Grader 严格过滤。建议配合**向量相似度预过滤**（`vecScore < 0.3` 直接跳过，不送 Grader），既省钱又降噪。

## 3. 🔗 实体链接难题（Graph RAG / Hybrid RAG）

> 涉及架构：Graph RAG、Hybrid RAG

### 3.1 精确匹配的局限

| 图谱中的实体 | 用户查询 | 精确匹配 | 模糊匹配 | 语义匹配 |
|------------|---------|---------|---------|---------|
| CRISPE 框架 | CRISPE框架 | ❌ 空格差异 | ✅ | ✅ |
| Chain of Thought | 链式思考 | ❌ | ❌ | ✅ |
| Chain of Thought | CoT | ❌ | ❌ | ✅ |
| CRISPE 框架 | 有哪些框架适合写提示词 | ❌ | ❌ | ✅ |

### 3.2 实体消歧的两阶段设计

为控制成本，分两阶段：

```
阶段1: 字符串级候选检测（0 次 LLM）
  ├─ 空格差异: "CRISPE 框架" ↔ "CRISPE框架" → 候选 ✅
  ├─ 后缀去除: "CRISPE框架" ↔ "CRISPE" → 候选 ✅
  └─ 字符重叠 > 70%: "CoT" ↔ "Chain of Thought" → 跳过 ❌

阶段2: LLM 逐对判断（仅候选对，通常 3-10 对）
```

- 候选检测 0 成本（纯字符串运算）
- LLM 判断只针对候选对（prompt 约 100 token）

### 3.3 实体链接兜底策略

```
查询 "CoT" → graph.has("CoT")? → ❌ 精确匹配失败
         ↓
   LLM 匹配: "图谱有 'CoT推理技术'、'CoT框架'，'CoT' 匹配哪个？"
         ↓
   返回 "CoT推理技术" → 精确命中 → BFS 遍历
```

> 仅当精确匹配失败时触发，正常查询 0 额外成本。

## 4. 💰 LLM 调用成本与质量权衡

> 涉及架构：全部

### 4.1 各架构成本对比

| 架构 | 每次查询 LLM 调用 | 典型耗时 | 成本等级 |
|------|------------------|---------|---------|
| Naive RAG | 1 次 | 1-2s | ⭐ |
| Multimodal RAG | 1+N 次（构建时 N 图片） | 1-5s | ⭐⭐ |
| HyDE | 2 次（假设回答 + 最终生成） | 2-3s | ⭐⭐ |
| Corrective RAG | TopK + 1 次（评分×K + 生成） | 3-6s | ⭐⭐⭐ |
| Graph RAG | 2 次/查询（route+NER + 生成） | 2-3s | ⭐⭐（查询） |
| Hybrid RAG | 2-3 次（NER + 兜底 + 生成） | 3-5s | ⭐⭐ |
| Adaptive RAG | 2-7 次 | 1-10s | 波动大 |
| Agentic RAG | 不确定（MAX_ITERATIONS=6 次） | 5-15s | ⭐⭐⭐⭐⭐ |

### 4.2 成本优化策略

**Graph RAG 的成本优化（典型）**：

| 优化措施 | 之前 | 之后 | 节省 |
|---------|------|------|------|
| 三元组+声明合并 | 2 次/chunk | 1 次/chunk | -50% |
| 路由+NER合并 | 2 次/查询 | 1 次/查询 | -50% |
| 实体消歧候选检测 | LLM 判断所有对 | 字符串过滤 → 仅候选 | -90%+ |

**Adaptive RAG 的迭代成本控制**：

| 优化措施 | 效果 |
|---------|------|
| 限制最大轮数（默认 3 轮） | 避免无限循环 |
| 每轮 Top-K 递减（5→3→2） | 后续轮次聚焦核心缺口 |
| 去重机制 | 避免重复检索 |
| 早期停止 | 信息充足时立即终止 |

**Corrective RAG 的 Top-K 调优**：

Top-K 每增加 1，每次查询多 1 次 LLM 调用。建议配合向量相似度预过滤（`vecScore < 0.3` 直接跳过）。

### 4.3 一次构建，多次查询

Graph RAG 和 Hybrid RAG 的**构建成本高，但查询快**：

| 阶段 | LLM 调用次数 | 缓存后 |
|------|-------------|--------|
| 实体抽取（每个 chunk 一次） | chunks.length 次 | 跳过 |
| 实体消歧（候选对） | candidates.length 次（~3） | 跳过 |
| 社区摘要（每个社区一次） | communities.length 次 | 跳过 |
| 每次查询 | 2-3 次 | 不变 |

## 5. 🗄️ 缓存设计演进

> 涉及架构：Graph RAG、Agentic RAG

### 5.1 Graph RAG 的缓存演进

| 阶段 | 缓存文件 | 问题 |
|------|---------|------|
| 最初 | 4 个独立文件 | 消歧结果未缓存，每次启动仍跑 LLM |
| 现在 | **1 个 `graph_index.json`** | 包含图+索引+社区+声明，一次跳过全部 |

### 5.2 Agentic RAG 的存储隔离

使用独立目录，避免与 Naive RAG 共享存储污染：

| 资源 | Naive RAG | Agentic RAG |
|------|----------|-------------|
| 持久化索引 | `storage/` | `storage_agentic/` |
| 切分缓存 | `cache/naive_nodes.json` | `cache/agentic_nodes.json` |

### 5.3 Multimodal RAG 的图片缓存

图片描述结果缓存到 `cache/image_descriptions.json`，避免重复调用 Vision LLM。

**教训**：缓存是 RAG 系统从原型到生产的关键一步，缓存的粒度（每个文件/全部合并）、生命周期、失效策略都需要提前设计。

## 6. 📝 Prompt 设计陷阱

> 涉及架构：Corrective RAG、Adaptive RAG、Agentic RAG

### 6.1 输出格式不一致

**问题**：LLM 的 JSON 输出不稳定，需要多层解析降级。

**Agentic RAG 的解决方案**：三层降级策略
```
LLM 输出
  │
  ├→ 策略1：提取 JSON 块
  │   ├→ 成功：解析出 structured thinking
  │   └→ 失败：降级到策略2
  │
  ├→ 策略2：正则匹配（Thought / Action / Finish 模式）
  │   ├→ 成功：兼容老版本格式
  │   └→ 失败：降级到策略3
  │
  └→ 策略3：默认 finish（不会死循环）
```

### 6.2 分类 Prompt 的模糊边界

**Adaptive RAG 的 Query Analyzer**：

| 错误类型 | 后果 |
|---------|------|
| Simple → Complex | 过度检索，浪费成本和时间 |
| Complex → Simple | 答案不完整，缺乏深度 |

**缓解措施**：
- 使用 Few-shot Learning 提升分类准确率
- 支持用户在答案不满意时手动触发"深入分析"
- 设置超时降级（Complex 超时 → 降为 Medium）

### 6.3 混合输出格式的兼容

**Agentic RAG 初始版本的问题**：

| 版本 | 输出格式 | 问题 |
|------|---------|------|
| 初始 | 混用 `TOKEN_NAME[...]` 和 JSON | 解析逻辑与 Prompt 描述矛盾 |
| 改进 | 统一 JSON + 3 层降级 | 旧格式兼容，新格式统一 |

## 7. 🔄 Token 爆涨与上下文管理

> 涉及架构：Agentic RAG、Graph RAG

### 7.1 Agentic RAG 的 Token 线性增长

每轮迭代需要完整 Prompt（含历史步骤），token 用量随轮数线性增长：

```
第1轮: [System Prompt + Tools] + [Question] + [History(空)] → [Thought+Action]
第2轮: [System Prompt + Tools] + [Question] + [第1轮历史] → [Thought+Action]
第3轮: [System Prompt + Tools] + [Question] + [第1-2轮历史] → ...
```

### 7.2 Graph RAG 的 Prompt Token 优化

生成 prompt 的构成演进：

| 上下文块 | 最初 | 优化后 | 理由 |
|---------|------|-------|------|
| 社区摘要 | ✅ | ✅ | 核心信息，保留 |
| 关系路径 | 20 条 | **5** 条 | 信息重复，5 条已够 |
| 原文片段 | 5 个 chunk | **❌ 移除** | 摘要已覆盖，省 ~5000 token |
| 声明 | 全部+置信度 | **10** 条，去掉置信度 | 截断冗余 |
| **合计** | **~5900 token** | **~900 token** | **省 85%** |

### 7.3 Anthropic 的解决方案

- **Orchestrator-Workers 架构**：Lead Agent 规划 → SubAgent 并行执行（独立的上下文窗口）
- **持外化记忆**：Agent 将关键信息写入外部存储，防止 context window 溢出
- **Rainbow 部署**：新旧版本并行，避免中断运行中的 Agent 会话
- **Token 预算分析**：token 用量解释了 **80%** 的检索性能差异，升级模型（Sonnet 3.7 → Sonnet 4）的效果 > 翻倍 token 预算

## 8. 🔀 双路检索融合问题（Hybrid RAG）

> 涉及架构：Hybrid RAG

### 8.1 跨系统打分的对齐问题

**向量检索**输出余弦相似度（0~1），**图谱检索**输出深度衰减分（0.4~1.0）。两种打分体系不同，直接平均分融合会引入偏差。

**解决方案**：RRF（Reciprocal Rank Fusion）

```
RRF_score(d) = Σ 1 / (k + rank_i(d))
```

- `k = 60`（标准 RRF 常数）
- 只关心排名位置，不关心分数绝对值
- 天然解决了跨系统打分对齐问题

### 8.2 图谱 BFS 深度调优

| BFS 深度 | 覆盖范围 | 噪声风险 | LLM 调用 |
|---------|---------|---------|----------|
| 0（仅精确实体） | 小 | 低 | 1 次（NER） |
| 1（一层邻居） | 中 | 中 | 1 次（NER） |
| 2（两层邻居） | 大 | 高 | 1 次（NER） |

**推荐**：深度 1，覆盖性和精确性的最佳平衡点。

### 8.3 社区摘要增强

融合后如果命中某个社区的实体，将社区摘要也加入上下文。社区摘要为 LLM 提供更高层次的"主题概览"，弥补单一片段信息碎片化的问题。

## 9. 🧠 Agent 系统设计挑战（Agentic RAG）

> 涉及架构：Agentic RAG

### 9.1 单次 vs 双次 LLM 调用

| 版本 | 每次迭代 LLM 调用 | 问题 |
|------|------------------|------|
| 初始 | 2 次：generateThought() + decideAction() | 效率低，推理状态可能丢失 |
| 改进 | 1 次：统一 JSON 输出 | 效率翻倍，一致性好 |

### 9.2 sources 收集 Bug

**原 Bug**：从格式化文本（Observation）中 `JSON.parse()` 收集 sources —— 但 Observation 是格式化后的文本，包含编号、相似度百分比等非 JSON 内容，`JSON.parse()` 永远失败。

**修复**：从 `rawResult`（工具原始返回值）直接收集。

### 9.3 安全计算器

| 方案 | 安全性 | 能力 |
|------|-------|------|
| ❌ `new Function("return ...")()` | ❌ 任意代码注入 | 完整 JS 表达式 |
| ✅ `safeMathEval()` 递归下降解析 | ✅ 仅支持 +-*/() | 四则运算 |

### 9.4 跨轮对话记忆

```typescript
interface ChatMemory {
  role: "user" | "assistant";
  content: string;
}
```

- 每轮记录用户问题 + 助手回答
- 最多保留最近 6 轮，避免 Prompt 过长

### 9.5 Agentic RAG 的局限性

1. **Token 消耗高** — 每轮迭代 Prompt 含历史步骤，token 随轮数线性增长
2. **错误级联** — 某轮判断失误，后续难以纠正
3. **LLM 可靠性** — JSON 格式一致性不稳定，需多层降级解析
4. **轮数限制** — `MAX_ITERATIONS = 5`，复杂任务可能不够
5. **观察截断** — 检索结果超过 500 字符被截断，Agent 可能看不到完整信息

## 11. 💡 经验教训汇总

1. **不要信任 LLM 的自觉性** — 靠 Prompt 引导不够，要把智能封装到工具内部（Poka-Yoke）
2. **先宽后窄** — 检索策略像人类专家：先探索全貌，再逐步聚焦
3. **并行替代串行** — 广度问题需要并行检索，串行 5 轮不如并行 1 次
4. **工具设计 > Prompt 设计** — Anthropic 在 SWE-bench 中工具优化投入远超 Prompt
5. **Token 预算是硬约束** — 多 Agent 系统 token 消耗是 chat 的 15 倍
6. **评分标准必须严格** — Grader 宽松会导致"高质量误判"
7. **路由决策用 maxScore 而非平均分** — 一个好 chunk 加 4 个噪声不应降级
8. **缓存是整个系统的关键** — 粒度、生命周期、失效策略需要提前设计
9. **一次构建，多次查询** — Graph RAG 构建慢（几分钟）但查询快（几秒）
10. **RFF 解决跨系统打分对齐** — 不关心分数绝对值，只关心排名位置
11. **检索→重排双阶段** — 向量检索（bi-encoder）保召回，LLM 重排序（模拟 cross-encoder）提精排
12. **重排序有阈值** — chunk 超过 12 个时成本过高，跳过重排回退向量分排序
