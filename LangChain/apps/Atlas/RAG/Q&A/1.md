## Agent （标量 + 向量混合检索方向）

---

### L1 基础理解

**Q1：请解释 RAG 中"标量检索"和"向量检索"的区别，各自的适用场景是什么？**

> 考察点：能否清晰区分精确匹配和语义匹配，是否理解各自的数据形式和查询方式。

**A1（得分 85/100 → 标准回答）：**

标量检索：基于确定值（字符串、数字、日期、枚举）做精确匹配，如 `author="张三"`、`date>2024-01-01`，典型工具是 ES、MySQL。

向量检索：基于 Embedding（一组浮点数）做语义相似性搜索，如 `[0.12, -0.34, 0.56, ...]` → 找语义相近文档，典型工具是 Milvus、Pinecone。

核心区别：标量 = 条件对不对，向量 = 意思像不像。

---

**Q2：为什么纯向量搜索在实际应用中往往不够用？请举一个具体例子说明。**

> 考察点：是否理解向量搜索"语义相近但条件不对"的问题，能否给出真实场景。

**A2（得分 90/100 → 标准回答）：**

纯向量搜索只看语义相似性，不保证精确条件。例如查询"2026年张三写的关于AI的文章"，向量搜索可能返回：2025年李四写的AI文章（语义相近但年份和作者都不对）、2026年张三写的AI文章（正确的那个被其他噪声挤到后面）。标量条件无法被向量搜索约束，所以需要标量筛选来保证"条件对"。

---

### L2 设计决策

**Q3：标量筛选和向量搜索的先后顺序对结果有什么影响？如果先向量再标量会怎样？**

> 考察点：是否理解"先标量缩范围，再向量找相关"这个顺序不是随意选的。先向量再标量会导致语义相近但不符合条件的文档被向量选中，然后被标量过滤掉，浪费计算且可能漏掉既符合条件又语义相关的文档。

**A3（得分 70/100 → 标准回答）：**

先标量再向量：在符合条件的子集里做向量搜索，计算量小，且不会遗漏既符合条件又语义相关的文档。

先向量再标量：在全集里做向量搜索取 top_k（比如前10篇），这10篇里可能大部分不符合标量条件。过滤后只剩2~3篇，而真正既符合条件又语义相关的文档可能在向量搜索时排在第11名以后，根本没被选进 top_k，直接丢失了。这是**漏召回**问题，不是简单的"浪费资源"。

---

**Q4：ES 本身也能做向量搜索，为什么实际中还要搭配专门的向量数据库？两者做向量搜索的差异是什么？**

> 考察点：是否了解 ES 的向量搜索是基于 HNSW 索引的实现，在向量维度高、数据量大时性能不如专门的向量数据库（如 Milvus 用更优化的索引结构和分布式架构），且 ES 的向量搜索精度和召回率通常也偏低。

**A4（得分 80/100 → 标准回答）：**

ES 做向量搜索用的是 HNSW 索引实现，三个核心短板：

1. **规模受限**：ES 单节点内存有限，向量数据量大时 HNSW 索引膨胀严重，容易 OOM
2. **精度偏低**：ES 的向量搜索是近邻搜索（ANN），召回率不如专用向量数据库的优化索引
3. **不支持向量专有优化**：如量化（PQ/SQ）、分片策略、多级索引等，Milvus/Pinecone 有这些

所以 ES 适合做标量检索 + 小规模向量搜索的"一站式"方案，大规模向量搜索应交给专用数据库。

### L3 工程实践

**Q5：在混合检索中，标量筛选后的文档数量可能很多（比如500篇），向量搜索应该返回多少篇？这个数量怎么确定？**

> 考察点：是否理解 top_k 的选择需要平衡——太少可能遗漏相关文档，太多会给 LLM 带噪声且增加 token 消耗。通常 top_k 在 5~20 之间，具体取决于 LLM 的上下文窗口和文档长度。

**A5（得分 75/100 → 标准回答）：**

top_k 的确定逻辑：

1. **先算 LLM 上下文窗口能装多少文档**：假设窗口 8K tokens，每篇文档平均 500 tokens，则最多装约 16 篇 → top_k 不应超过 16
2. **再考虑噪声容忍度**：top_k 越大，后面几篇相关性越低，噪声越多。一般取 5~10 篇质量较好
3. **最后看标量筛选后的候选量**：如果候选只有 50 篇，top_k=10 就够了；如果候选有 500 篇，可以适当提高到 top_k=20，然后用 Reranking 过滤

公式化思路：`top_k = min(上下文容量 / 文档平均长度, 噪声容忍上限)`

---

**Q6：假设标量筛选后只剩3篇文档，但用户的问题需要至少10篇候选才能覆盖，你会怎么处理？**

> 考察点：是否理解当标量条件过严导致候选太少时的降级策略——放宽标量条件（比如去掉某个 filter）、扩大向量搜索范围、或回退到纯向量搜索。

**A6（得分 85/100 → 标准回答）：**

降级策略按优先级：

1. **优先放宽标量条件**：去掉最不重要的 filter（比如去掉"标签=技术"，保留"作者=张三"和"年份=2026"），重新筛选看候选是否够
2. **如果放宽后仍不够**：回退到纯向量搜索，不带标量条件，在全集里做语义搜索
3. **兜底**：如果纯向量搜索结果也不够，告诉用户"当前没有足够相关文档"，不强行拼凑低质量文档

核心原则：宁可少返回高质量的，也不要多返回低质量的凑数。

---

**Q7：标量 + 向量混合检索的结果如何合并？是简单拼接还是需要加权/排序？请给出你的设计思路。**

> 考察点：是否理解合并策略——常见做法是标量筛选后直接在候选集里做向量搜索（顺序执行），而不是两个独立搜索后合并。如果是两路独立搜索后合并，就需要 Reranking 来统一排序。

**A7（得分 80/100 → 标准回答）：**

三种合并方案，按推荐度排列：

**方案1（推荐）：顺序执行**
标量筛选 → 缩小候选集 → 在候选集里做向量搜索 → 返回 top_k。这是最常见也最干净的方案，不需要额外合并逻辑。

**方案2：两路并行搜索 + Reranking**
标量搜索返回 N 篇，向量搜索返回 M 篇，两路结果可能有重叠也有独有。合并后用 Reranking 模型统一重排。适合标量条件和语义条件都很重要、且两路结果可能有互补的场景。

**方案3（不推荐）：简单拼接**
把标量和向量结果直接拼接，不做排序。质量差，噪声多。

实际选哪种取决于业务场景和数据规模。方案1是默认选择。

### L4 深水区

**Q8：这段材料还提到了重排（Reranking）、多跳 RAG 和 Graph-RAG。请解释 Reranking 在标量 + 向量混合检索流程中放在什么位置、起什么作用？**

> 考察点：是否理解 Reranking 是在向量搜索之后、送入 LLM 之前的一个中间步骤，用专门的重排模型对候选文档做更精细的评分排序，把真正相关的文档排到前面，减少噪声文档对 LLM 的干扰。

**A8（得分 85/100 → 标准回答）：**

Reranking 位于流程的**向量搜索之后、送入 LLM 之前**。

作用：向量搜索的分数（cosine similarity）是**粗粒度**的，只看整体语义接近度。Reranking 模型（如 Cohere Rerank、bge-reranker）做的是**细粒度**的 query-document 相关性评分，它会考虑查询和文档的具体语义交互，把真正回答了用户问题的文档排到前面。

例子：向量搜索可能给"贪吃蛇游戏规则文档"打分 0.89，给"贪吃蛇引擎开发故事"打分 0.87，分数接近。但用户问的是"贪吃蛇怎么玩"，Reranking 会把游戏规则排到引擎故事前面，因为前者才真正回答了问题。

---

**Q9：如果用户的问题是"2026年张三写的贪吃蛇文章和2025年李四写的贪吃蛇文章有什么区别"，单次标量+向量检索能解决吗？需要什么额外机制？**

> 考察点：是否识别出这是**多跳查询**——需要分两次检索（一次筛张三2026、一次筛李四2025），然后对比合并。单次检索无法同时满足两组不同条件并做对比。

**A9（得分 90/100 → 标准回答）：**

单次标量+向量检索无法解决，因为条件分两组（张三2026 / 李四2025），需要：

1. **查询解析**：识别出这是一个多条件对比问题，拆解成两个子查询
2. **多跳检索**：分别执行两次标量+向量检索（一次 `author=张三 AND year=2026`，一次 `author=李四 AND year=2025`）
3. **结果合并与对比**：将两路结果送入 LLM，让 LLM 基于两组文档做对比回答

这就是多跳 RAG 的典型场景——单跳的标量+向量只能处理单一条件组合，多跳处理多条件组合+对比。

---

**Q10：标量 + 向量混合检索和 Graph-RAG 能结合吗？如果结合，图在哪个阶段发挥作用？**

> 考察点：是否理解 Graph-RAG 的图主要在**文档处理阶段**发挥作用——提取实体和关系构建知识图谱，然后在检索阶段可以通过图的关系路径找到更多相关文档（比如从"贪吃蛇"这个实体出发，沿关系边找到"对战引擎""WebSocket"等相关实体对应的文档），扩展召回范围。标量+向量解决的是"精确筛选+语义匹配"，图解决的是"关系推理扩展召回"。

**A10（得分 85/100 → 标准回答）：**

可以结合，图在两个阶段发挥作用：

**阶段1：文档处理阶段（构建图）**
用 LLM 从文档中提取实体和关系，构建知识图谱。比如从贪吃蛇文章中提取实体"贪吃蛇"、"对战引擎"、"WebSocket"，关系"贪吃蛇-使用-对战引擎"、"对战引擎-基于-WebSocket"。

**阶段2：检索阶段（利用图扩展召回）**
当用户查询"贪吃蛇引擎的技术难点"，向量搜索可能只召回直接提到"贪吃蛇引擎"的文档。但通过图的关系路径：贪吃蛇 → 对战引擎 → WebSocket → 内存释放策略，可以**沿边扩展**找到更多相关文档（WebSocket 相关的、内存管理相关的），补充向量搜索的召回盲区。

三者分工：标量=精确筛选，向量=语义匹配，图=关系推理扩展召回。
